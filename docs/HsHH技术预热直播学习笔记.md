## 0. 先用一分钟看懂整个系列

这几场直播其实在回答四个连续的问题：

1. **我完全不懂硬件，能不能参加？**  
   能。先从真实生活问题出发，不必先成为电子工程师。
2. **怎样让一块开发板运行起来？**  
   用 TuyaOpen IDE 完成创建产品、编译、烧录、授权和联网。
3. **怎样让 AI 不只是聊天，而是真的控制设备？**  
   用 Astron Agent 和工作流，把“理解意图—读取数据—作出判断—执行动作—反馈结果”串起来。
4. **不会选元件、接线和写嵌入式代码怎么办？**  
   可以借助 STACK ANYWAY，让 AI 帮助选型、接线、编程和排错，但人仍要做安全检查和实际操作。

四场内容合起来，就是一条完整路线：

```text
发现生活问题
    ↓
定义一个小而明确的产品
    ↓
选择开发板、传感器和输出装置
    ↓
让开发板编译、烧录并联网
    ↓
让 AI 读取信息、作出判断、控制硬件
    ↓
做出一个能稳定演示的 Demo
    ↓
继续优化外壳、体验、市场和量产
```

最重要的一句话：**黑客松不是考你已经会多少，而是看你能否在有限时间里，把一个真实想法做成可以验证的 Demo。**

# 第一场：硬件小白如何从创意到产品落地

## 1.1 这一场想解决什么问题

很多人一听“硬件黑客松”，会以为必须先学会焊接、画电路图、做 PCB、写底层程序。第一场分享主要是打破这种恐惧：现在有现成开发板、传感器模块、开源代码和 AI 工具，普通人也可以从一个想法开始做硬件原型。

这里要区分两个目标：

- **Demo（演示原型）**：证明核心想法能运行，比赛期间追求的是这个。
- **量产产品**：要考虑成本、可靠性、认证、供应链和售后，是比赛以后才逐步处理的事。

你在黑客松里不需要完成一台可以立刻出售的产品。只要让评委看见“问题真实、方案合理、核心闭环跑通”，就已经很有价值。

## 1.2 创意应该从哪里来

分享者建议从真实生活出发，而不是为了使用某项技术硬凑场景。好的起点可以是：

- 一个你反复遇到的小麻烦；
- 一段使用现有产品时很别扭的经历；
- 某类人长期被忽略的需要；
- 一个很有趣、能带来情绪价值的互动；
- 一个过去难以实现、现在可以借 AI 实现的想法。

例如，“做一个有摄像头的 AI 设备”仍然太宽。更好的描述是：

> 帮助独居老人确认是否按时吃药。用户把药盒放到摄像头前，设备识别药物和时间，屏幕显示结果，并通过声音提醒。

后者已经说明了用户、场景、输入、判断和输出。

### 一个好想法的五个问题

1. 谁会使用它？
2. 用户在什么场景中遇到什么困难？
3. 设备怎样获得信息？
4. AI 或程序需要判断什么？
5. 设备最后做出什么看得见或听得见的动作？

如果这五个问题答不清，先不要买模块或写代码。

## 1.3 传统硬件开发为什么难

传统硬件产品通常需要多种专业能力：

- **硬件工程**：选择芯片、设计电路、接传感器；
- **嵌入式软件**：给芯片写程序；
- **结构设计**：设计外壳、尺寸和内部空间；
- **算法与云服务**：处理图像、语音或数据；
- **供应链与量产**：采购、生产、质检和认证；
- **产品与市场**：理解用户、设计体验、讲清价值。

过去一个人很难同时掌握这些能力。现在的变化不是这些知识消失了，而是：

- 开发板把许多复杂电路预先做好；
- 模块化传感器减少了从零设计电路的需要；
- 开源 SDK 提供现成代码和示例；
- AI 可以帮助阅读文档、生成代码、分析日志和提出接线方案；
- 团队协作可以让不同人负责不同部分。

因此，硬件小白可以先站在**用户和产品**的角度推动项目，再向工具、队友和技术老师求助。

## 1.4 本次使用的核心开发板：涂鸦 T5 方案

直播介绍的比赛开发板以涂鸦 T5 模组为核心。可以把开发板理解成一台没有普通电脑那么完整、但非常适合控制设备的“小电脑”。

它的主要能力包括：

- Wi‑Fi：连接网络和云服务；
- 蓝牙：近距离配网或通信；
- 麦克风：接收声音；
- 喇叭：播放声音；
- 摄像头：获取图像；
- 屏幕：显示文字、图片和状态；
- GPIO、I²C、SPI、UART 等接口：连接传感器、灯、电机等模块。

这里不需要马上记住接口细节。初学者先理解：**开发板负责计算和协调，传感器负责感知，执行器负责产生现实动作。**

例如：

```text
温湿度传感器 → T5 开发板 → AI/规则判断 → 屏幕和喇叭提醒
```

## 1.5 比赛提供什么，自己准备什么

根据直播口径，主办方会提供开发板和许多常用模块，现场可以使用；如果自己的创意需要清单之外的模块，可以提前购买并带到现场。

但是以下事项必须向主办方最终确认：

- 实际发放或现场提供的具体模块清单；
- 开发板寄送对象和寄送时间；
- 设备赛后能否带走；
- 住宿、餐饮和场地安排；
- 最终报名、组队、提交和评审规则。

直播中的口头回答有些是分享者推测，不应当作最终规则。

## 1.6 怎样组队

推荐团队包含以下能力，但不要求一人只做一个角色：

- 产品与用户研究：定义真实问题、控制范围；
- 硬件：接线、模块调试；
- 软件与 Agent：代码、接口、工作流；
- 结构与视觉：外壳、交互、海报；
- 表达与路演：PPT、视频、答辩。

小白并不是“没有用的人”。能发现真实问题、组织团队、设计体验、测试产品、制作展示，同样是关键工作。

## 1.7 第一场最值得记住的结论

- 不要先学完全部知识再开始，先选一个小问题做原型。
- 好作品的最大门槛往往是想法是否真实、具体，而不只是技术难度。
- 黑客松时间短，核心是做 Demo，不是做完量产产品。
- 团队中只要有成员能处理基础硬件，其他人可以负责产品、软件、外观和展示。
- 比赛以后，如果 Demo 有潜力，还可以继续寻找制造、众筹、投资和渠道支持。

# 第二场：用 TuyaOpen IDE 让 AI 创意跑上真实硬件

## 2.1 这一场的核心任务

第二场是一场实操课，目标是完成下面这条链路：

```text
创建云端产品
  → 创建代码项目
  → 编译程序
  → 把程序烧录进开发板
  → 给设备写入授权
  → 手机配网
  → 设备联网并开始对话
```

这一场术语很多，但本质上是在做两件事：

1. 把程序装进开发板；
2. 让开发板获得合法身份并连接涂鸦云端。

## 2.2 先认识几个关键名词

### IDE

IDE 是“集成开发环境”。可以把它理解成程序员的综合工作台，里面可以编辑代码、编译、烧录和查看日志。

TuyaOpen IDE 以插件形式安装到 VS Code、Cursor 等编辑器中。它把 TuyaOpen SDK、编译、烧录、授权和 AI 辅助功能放到同一个环境里。

### SDK

SDK 是一套开发工具和代码库。它已经写好了联网、控制外设等基础能力，你不必从零发明。

### 产品 PID

PID 是 Product ID，可以理解成某一类产品在涂鸦平台上的“型号身份证”。它告诉云端：这是什么产品、有哪些功能。

### 授权码

授权码用于给具体设备分配可连接涂鸦云的身份。直播中提到它由 UUID 和 Key 等信息组成。可以粗略理解为设备的“身份证和密钥”。

### 编译

人写的代码不能直接被芯片理解。编译就是把代码翻译成芯片可以运行的固件。

### 烧录

烧录就是把编译出的固件写入开发板。它类似给设备安装系统或应用程序。

### 串口与日志

串口是一种设备通信方式。开发板运行时会输出日志，日志就像设备的“体检报告”或“运行日记”，可以帮助判断程序运行到哪里、哪里出错。

### 配网

配网是把 Wi‑Fi 信息告诉设备，让设备连接网络。直播示例通过手机蓝牙发现设备，再发送 2.4GHz Wi‑Fi 信息。

## 2.3 TuyaOpen IDE 为什么对初学者有帮助

传统方式可能需要手动安装编译器、下载 SDK、设置环境变量、配置烧录工具。TuyaOpen IDE 尽量把这些步骤整合起来，还可以让 AI：

- 创建产品；
- 了解开发板上哪些引脚已经占用；
- 编译和烧录；
- 读取日志；
- 根据功能点辅助开发设备代码或手机面板；
- 导入传感器驱动示例。

但 AI 不是魔法。它仍然需要正确的板卡型号、模块型号、PID、接线信息和错误日志。

## 2.4 赛前安装准备

建议比赛前完成：

1. 注册涂鸦开发者平台账号；
2. 安装 VS Code、Cursor 或其他兼容编辑器；
3. 下载 TuyaOpen IDE 的 `.vsix` 插件包；
4. 在编辑器命令面板中选择“从 VSIX 安装扩展”；
5. 打开 TuyaOpen IDE 首页；
6. 在左下角登录涂鸦开发者账号；
7. 检查编译、烧录、清理、日志等入口是否出现；
8. 手机安装“涂鸦”或“智能生活”App；
9. 准备一根确定能传输数据的 Type‑C 线。

为什么必须提前安装？因为比赛现场才下载，可能遇到网络慢、系统权限、插件兼容或驱动问题。

## 2.5 从示例跑通设备的完整步骤

### 第一步：创建或复制产品

可以在涂鸦开发者平台手动创建，也可以在 TuyaOpen IDE 中让 Agent 帮助创建。

初学者适合先复制官方 OEM 示例，因为它已经准备了常见功能点；完全自定义产品自由度更高，但需要自己配置更多内容。

重要注意事项：**产品名称必须独特。**

比赛现场会有很多设备同时通过蓝牙配网，如果大家都使用默认名称，很可能认不出自己的设备。建议使用：

```text
队名-项目名-编号
```

### 第二步：记录 PID

创建产品后复制 PID，并准确填入示例项目。PID 写错，代码可能编译成功，但设备不能按预期关联到产品。

如果更换 PID，应先执行 Clean（清理），再重新编译，确保旧配置没有被缓存。

### 第三步：领取授权码

进入涂鸦开发者平台中对应产品的硬件开发页面，按官方文档领取免费开发者授权码。直播演示选择“授权码清单”的交付方式。

授权码属于设备身份信息，不应随意公开或提交到公共代码仓库。

### 第四步：导入或创建示例项目

收到比赛开发板后，优先使用官方为该板卡准备的示例。示例已经打通部分语音、摄像头和云端能力，比从空项目开始稳定。

### 第五步：连接硬件

- 检查摄像头、麦克风、喇叭接口；
- 使用可传数据的 Type‑C 线连接电脑；
- 确认设备电源开关已打开；
- 确认电脑出现对应串口。

“板子亮了”只说明有供电，不一定说明数据线能够通信。

### 第六步：编译和烧录

可以点击 IDE 中的按钮，也可以让集成的 Agent 执行。推荐第一次手动观察整个过程，记录成功时的板卡、端口和配置。

编译失败与烧录失败是两类问题：

- 编译失败通常与代码、依赖、环境或配置有关；
- 烧录失败通常与数据线、串口、驱动、板卡状态或端口占用有关。

### 第七步：写入设备授权

在 IDE 中选择授权功能，选择正确的授权码和开发板串口。

直播在 Mac 上演示了类似 `cu...` 的串口名称，但不同电脑名称可能不同。不要机械照抄；拔掉开发板再插回去，观察哪个端口新增，是常用的判断方法。

如果烧录成功却无法在 App 中发现设备，首先检查授权是否成功。

### 第八步：手机配网

1. 手机连接 2.4GHz Wi‑Fi；
2. 打开手机蓝牙；
3. 打开“涂鸦”或“智能生活”App；
4. 点击右上角加号添加设备；
5. 选择自己设置的产品名称；
6. 等待设备联网。

为什么强调 2.4GHz？很多 IoT 设备只支持 2.4GHz Wi‑Fi，不支持或不能直接使用 5GHz 网络。

### 第九步：测试官方 Demo

官方 Demo 展示了多种语音交互模式，例如按住说话、按键开始对话、唤醒词对话和允许打断的连续对话。开发板侧面的 Button 可以切换模式，具体以收到的固件说明为准。

示例还支持摄像头、麦克风、喇叭和屏幕等资源，为后续创意提供基础。

## 2.6 重新配网与按键操作

直播示例中，换手机绑定或重新配网时，可以连按背面 Reset 三次，每次间隔约 1～2 秒，使设备重新进入配网状态。

这属于当时 Demo 固件定义的行为。若团队修改了按键程序，操作可能发生变化，最终以项目代码和官方说明为准。

## 2.7 串口为什么容易出问题

直播提到 T5 模组有多路 UART，但比赛板卡实际引出的串口数量和用途有限。有的串口用于烧录，有的用于输出日志。如果程序把日志发送到没有连接电脑的串口，设备可能实际在运行，但电脑看不到日志。

初学者不用立即修改底层串口代码。遇到“能烧录、看不到日志”时，应先提供：

- 开发板完整型号；
- 当前示例名称；
- IDE 和系统版本；
- 串口列表截图；
- Type‑C 接口和接线照片；
- 是否修改过日志串口；
- 完整报错。

再请技术老师帮助判断，不要盲目复制直播中的代码片段。

## 2.8 第二场最值得记住的结论

- 先跑通官方 Demo，再改造成自己的项目。
- 创建产品时必须使用独特名称。
- PID 改变后执行 Clean，再重新编译。
- 烧录、授权、配网是三个不同步骤；烧录成功不代表联网成功。
- 手机配网时开启蓝牙并使用 2.4GHz Wi‑Fi。
- 日志、截图、接线照片是求助时最有价值的信息。

# 第三场：用 Astron Agent 驱动真实硬件

## 3.1 为什么给硬件加一个聊天框还不够

普通聊天机器人主要负责回答问题，但 AI 硬件还需要操作现实世界。用户说“房间太闷了”，设备不能只回答“建议通风”，它可能还需要：

1. 读取温度、湿度或空气质量；
2. 判断是否真的超过阈值；
3. 检查设备是否允许执行；
4. 打开风扇或发出提醒；
5. 确认动作有没有完成；
6. 把结果告诉用户。

这就是从“会说话”走向“能完成任务”。

## 3.2 Agent、工作流、插件和硬件怎样分工

可以把整个系统想象成一个小团队：

- **Agent 是大脑和协调者**：理解用户想做什么，选择下一步。
- **工作流是流程图**：规定先做什么、遇到不同情况走哪条路。
- **插件/API 是翻译员**：把 Agent 的请求变成硬件能理解的命令。
- **硬件是感官和手脚**：读取真实数据、执行动作、反馈结果。

完整链路通常是：

```text
用户自然语言
  → Agent 理解意图
  → 工作流读取传感器或设备状态
  → 规则/模型作出判断
  → 插件调用硬件 API
  → T5 和外接模块执行动作
  → 设备上报成功或失败
  → Agent 向用户反馈
```

## 3.3 四个核心环节：感知、决策、执行、反馈

### 感知

从麦克风、摄像头、按钮、温湿度传感器等取得信息。原始数据可能是数字或 JSON，Agent 可以将它解释成人能读懂的结论。

### 决策

把传感器数据、用户目标、设备状态和安全规则综合起来，决定下一步。

例如不能只凭用户一句“很热”就永远打开风扇，还要检查温度、风扇是否在线、当前是否已开启，以及是否存在危险情况。

### 执行

通过 API 控制屏幕、LED、喇叭、电机或其他装置。硬件动作必须是确定、可检查的命令，例如：

```json
{
  "action": "set_light",
  "brightness": 40
}
```

而不是模糊的“让灯看起来舒服一点”。模糊目标可以由 AI 理解，但真正发给硬件时要转换成明确参数。

### 反馈

执行命令后，需要知道动作是否成功。否则系统可能告诉用户“灯已经打开”，但设备实际离线。

反馈可以包括：成功、失败、超时、设备离线、参数不支持等。

## 3.4 自由 Agent 与固定工作流的区别

直播比较了两种做法。

### 自由 Agent

由 AI 自己规划步骤、选择工具并执行。

优点：灵活，适合开放问题。  
缺点：结果不一定稳定，相同输入可能走不同路径。

### 固定工作流

由人事先把节点和分支设计好。

优点：可预测、容易测试，适合比赛演示和安全操作。  
缺点：每条规则都要设计，复杂项目会比较费时。

比较稳妥的混合方式是：

- 用大模型理解自然语言、分类或生成表达；
- 用代码节点做确定计算；
- 用条件节点执行明确规则；
- 用受限制的工具节点控制硬件。

原则是：**能用明确计算解决的事情，不要让模型猜；涉及安全的动作，不要只靠模型自由判断。**

## 3.5 Astron Agent 工作流中的常见节点

- 开始节点：接收用户输入；
- 结束节点：输出最终结果；
- 大模型节点：理解、分类、总结或生成内容；
- 代码节点：做数学计算、格式转换和稳定逻辑；
- 知识库节点：查找特定资料；
- 工具/插件节点：调用外部 API 或硬件；
- 条件节点：根据结果选择不同分支；
- 变量转换节点：存储、拼接和转换数据；
- 消息节点：在过程中向用户显示提示。

初学者可以从五个节点开始：

```text
开始 → 读取传感器 → 条件判断 → 控制设备 → 结束
```

## 3.6 为什么要先用 Mock，再接真实硬件

Mock 是模拟数据或模拟接口。假设真实温湿度传感器还没接好，可以先让一个接口固定返回：

```json
{
  "temperature": 31,
  "humidity": 75,
  "device_online": true
}
```

然后先检查：

- 工作流能否读取字段；
- 高温条件是否走正确分支；
- 参数是否传给执行节点；
- 异常情况有没有处理；
- 最终反馈是否正确。

推荐三步：

1. 固定 JSON：验证最基本逻辑；
2. Mock API：验证真实接口形式和字段；
3. 真实硬件 API：最后替换数据来源。

这样能区分到底是 Agent 工作流错误，还是接线、驱动和硬件错误。

## 3.7 一个适合高中生的示例

项目：专注学习提醒灯。

需求：学习时如果环境太暗，灯提醒用户调整照明；专注一段时间后提醒休息。

工作流：

```text
用户按下开始按钮
  → 读取光照传感器
  → 如果光照过低，LED 变黄并语音提醒
  → 开始计时
  → 到达设定时间，LED 变蓝并播放休息提醒
  → 用户按键确认
  → 记录完成并结束
```

这里 AI 可以理解用户说的“我想学习半小时”，代码节点负责把半小时转换成秒，工作流负责计时和分支，硬件负责灯光、按钮和声音。

## 3.8 可靠性和安全性

直播后半部分强调，真正迭代产品时要注意：

- Agent 与设备尽量解耦：业务规则放在 Agent/服务端，设备负责数据和动作；
- API 版本保持兼容，例如从 `/api/v1` 开始管理；
- 不要假设所有设备永远具有相同能力，可以先查询设备支持什么；
- 对危险动作设置边界，不让模型直接越过安全检查；
- 记录每一步输入和输出，便于排错；
- 处理设备离线、超时、重复调用和执行失败。

高中生阶段不必实现完整企业系统，但至少要处理三个情况：

1. 设备不在线怎么办？
2. 传感器没有返回数据怎么办？
3. 动作执行失败时，是否会误报成功？

## 3.9 第三场最值得记住的结论

- AI 硬件不是“聊天框 + 开发板”，而是一条感知、判断、执行和反馈的闭环。
- 模型负责理解和生成，确定逻辑交给代码或固定规则。
- 硬件命令应当明确、可检查，不使用模糊表达。
- 先用 Mock 验证软件链路，再换成真实硬件。
- 一个可靠系统不仅考虑成功流程，也考虑离线、超时和失败。

## 4.1 这一场想解决什么问题

硬件小白即使有了创意，还会遇到四个现实问题：

1. 应该买哪些板卡和模块？
2. 元件之间怎样接线？
3. 嵌入式代码怎样写？
4. 接好以后没有反应，怎样排错？

STACK ANYWAY 的定位是一个通过自然语言辅助硬件设计和实现的平台。用户描述想法后，AI 可以帮助进行元件选型、布局、接线、代码生成和调试。

直播提供的入口信息：

- 官网：<https://stack-anyway.com/>
- 邀请码：`SAWAIC2026`

## 4.2 Design Mode：从想法到硬件方案

在设计模式中，用户可以描述需求，例如：

> 我想做一个口袋电子宠物。它能感知走路、摇晃和倾斜，屏幕里的宠物会随动作变化，还能发出声音。

AI 接下来可以帮助：

- 把模糊想法拆成具体功能；
- 推荐主控板、姿态传感器、屏幕和喇叭；
- 考虑供电和尺寸；
- 生成接线关系；
- 根据新需求替换或增加元件；
- 形成物料清单。

平台的三维空间采用接近真实尺寸的布局，因此可以提前发现“元件虽然功能合适，但装不进外壳”这类问题。

## 4.3 Code Mode：从接线方案到程序

设计完成后，Code Mode 可以读取已经选择的板卡、元件和接线关系，再生成对应代码、安装依赖库、编译、烧录并读取调试信息。

用户还可以放入图片、音频或视频作为效果参考。例如想让屏幕显示某种动画、让设备播放某段声音，可以将参考资料交给 AI，帮助转化成程序中的资源和行为。

## 4.4 AI 怎样帮助排查硬件故障

硬件调试同时涉及虚拟世界和现实世界。代码可能正确，但现实中的线接错了；线看似正确，但接口、电压或通信协议不匹配。

平台可能通过这些方式辅助：

- 读取编译和串口日志；
- 扫描或测试引脚；
- 生成额外调试程序；
- 根据特定板卡的高频问题给出检查顺序；
- 提醒 Type‑C 接口是否插错；
- 指导用万用表测量某个引脚的电压；
- 对比预期信号和实际结果。

推荐排错顺序：

1. 是否正确供电？
2. 数据线是否能传数据？
3. 板卡和串口是否选对？
4. 模块电压是否兼容？
5. 接线是否与引脚图一致？
6. 通信协议和地址是否正确？
7. 驱动库和示例是否匹配？
8. 日志在哪一步停止？
9. 使用最小测试程序时，单个模块能否工作？

排错时一次只改变一个条件，否则即使突然成功，也不知道是哪项修改起了作用。

## 4.5 AI 生成的电路能直接相信吗

不能无条件相信。AI 可以快速提供候选方案和检查思路，但仍可能：

- 认错板卡版本；
- 使用错误或不存在的引脚；
- 忽略 3.3V 与 5V 的电压差异；
- 推荐已停产或不兼容的模块；
- 忽略电机等负载需要独立供电；
- 生成能编译但行为错误的代码。

所以要采用“AI 建议—查官方资料—小范围测试—真人复核”的方式。

特别是涉及锂电池、交流电、电热器件、大电流电机时，不应由没有经验的学生自行接线。比赛初次作品尽量使用主办方提供的低压模块，并请硬件老师确认。

## 4.6 与涂鸦 T5 怎样配合

直播说明 STACK ANYWAY 是开放平台，可以在 Code Mode 中直接说明正在使用涂鸦 T5 或比赛指定板卡。平台如果已经录入该板卡的尺寸、引脚和生态资料，建议会更准确；如果尚未完整录入，也可以结合用户提供的资料尝试生成代码和调试方案。

实际使用时应明确提供：

- 开发板完整型号和版本；
- 官方引脚图或产品链接；
- 已连接的模块完整型号；
- 每根线连接到哪个引脚；
- 供电电压；
- 已经占用的引脚；
- 当前代码和完整日志。

## 4.7 第四场最值得记住的结论

- 自然语言可以帮助小白完成选型、接线、代码和排错，但不会代替实际动手。
- 先在设计模式确定功能和物料，再进入代码模式实现。
- 板卡型号、引脚、电压和接线信息越准确，AI 的建议越可靠。
- AI 给出的电路必须结合官方文档和真人检查。
- 排错时先缩小问题，用最小程序单独测试一个模块。

# 7. 初学者最容易踩的坑

## 坑一：想法太大

“照顾所有人的全能健康机器人”无法在短时间内完成。缩小到一个人、一个场景、一个动作。

## 坑二：一开始就自定义全部内容

先跑官方示例，再每次改一个功能。基础链路没通之前大改代码，很难判断错误来自哪里。

## 坑三：把 AI 当成永远正确的工程师

AI 会编造引脚、接口和函数。重要结论要查开发板官方文档，危险接线要请真人复核。

## 坑四：只准备成功路线

比赛现场网络、云服务、蓝牙和硬件都有可能失败。必须准备录屏、视频、截图或 Mock 版本作为备用演示。

## 坑五：没有保存稳定版本

每完成一个里程碑就保存版本：

- 能编译；
- 能烧录；
- 能配网；
- 能控制一个模块；
- 能跑完整闭环。

演示前不要在唯一可用版本上冒险修改。

## 坑六：求助信息太少

“它坏了”不能帮助老师判断。应提供电脑系统、IDE 版本、板卡型号、模块型号、接线照片、完整日志、复现步骤和已经尝试的方法。

## 坑七：只重技术，不讲用户价值

评委需要知道为什么有人需要它。路演顺序建议是：用户问题 → 现有方式不足 → 你的方案 → 现场演示 → 技术实现 → 未来计划。

# 10. 最终总结

四场直播不是让你一次性记住所有工具，而是在教一种做产品的方法：

1. 从自己的真实生活寻找问题；
2. 把问题缩小到一个能够演示的场景；
3. 使用现成开发板和模块，不从零制造所有东西；
4. 先跑通官方示例，再逐步替换成自己的功能；
5. 让 AI 负责理解和辅助，让固定代码与规则保证稳定；
6. 把感知、判断、执行和反馈连成完整闭环；
7. 每次只解决一个问题，并保留稳定版本；
8. 用清楚的用户故事和稳定演示，让别人理解作品的价值。
